# Architecture Constraints and Candidate Design

## Stack selection is a milestone, not a presupposition
At M0 Codex must evaluate Swift/SwiftUI, Python/PySide6, and Tauri/React/Rust, including macOS EventKit, Keychain, notifications, packaging, OAuth callback handling, test tooling, AI/document parsing, and maintainability. Record selection in `docs/DECISIONS.md` before major implementation.

## Logical components
1. Desktop UI: onboarding, timeline, review inbox, assignment/task view, plan editor, sync health, preferences.
2. Local application service: orchestration, jobs, permissions, error reporting.
3. Integration adapters: Canvas REST API, Microsoft Graph API, Apple EventKit.
4. Normalization and provenance: canonical event/task schema, deduplication, timezone normalization, source records.
5. AI gateway: pluggable providers, structured outputs with schema validation, content minimization, prompt-injection resistance.
6. Planning engine: deterministic hard constraints and prioritization; AI provides task breakdown/effort estimates, not unchecked calendar mutations.
7. Local database: SQLite or equivalent with migrations, audit history, sync cursors, task state, user preferences.
8. Credential service: macOS Keychain.
9. Future cloud boundary: optional sync/notification workers behind interfaces, no cloud dependency for MVP.

## Core data flow
Canvas/Graph -> sync adapters -> source records -> normalization + dedup -> classification/extraction -> review/conflict detection -> canonical tasks/events -> AI task decomposition -> constraint scheduler -> proposed plan -> approval policy -> dedicated Apple Calendar.

## Scheduling invariants
- `AcademicDataset` scopes both assignments and fixed commitments before planning, and supplies the same scoped records to Timeline and Review Inbox. The default is Live data; Demo Mode is an explicit session choice. Switching clears the proposal. No storage deletion or status reset is involved.
- Scope follows stored source provenance, never event titles. Existing `Canvas` and `Outlook` sources are live; known sample source IDs and `Canvas (sample)`/`Outlook (sample)` providers are demo. Every referenced source must resolve to the chosen mode; unknown/mixed provenance is excluded, with records preserved. Future adapters must define their origin before their records enter planning.
- Fixed events and user-defined protected hours are hard constraints.
- No overlapping AI-managed blocks, no calendar writes without appropriate permissions.
- Deadlines are hard endpoints unless explicitly marked uncertain.
- Prefer early progress and buffer time; show unallocated work explicitly.
- User overrides outrank AI proposals; preserve original source facts.
- Any change affecting protected commitments requires explicit confirmation.

## Near-real-time caveat
Microsoft Graph change notifications may require a publicly reachable HTTPS endpoint and subscription lifecycle management; Canvas may not expose equivalent per-user push events. MVP should use robust polling/delta sync with backoff and catch-up. Evaluate push mechanisms separately and do not promise instant delivery while Mac is off.

## Test strategy
Unit tests for extraction schemas, date parsing, deduplication, conflict policies, scheduler invariants; mocked integration tests for Canvas/Graph/EventKit; manual smoke tests on macOS; permission-denial and offline cases; DST regression fixtures; provider failures; calendar rollback tests.


## Current implementation boundary (2026-10-19)

The app uses SwiftUI, a Swift domain library, and SQLite. `CanvasImporter` is read-only and transport-injected; it retrieves active courses, course assignments, and course calendar events. Canvas supplies pagination links but does not expose a shared delta cursor for these endpoints, so each sync refreshes the relevant course and event windows and merges by stable provider/external IDs. This is an idempotent local merge, not a server-side delta feed. After a fetch, `LocalDatabase.importCanvas` reconciles in the same transaction: records inside the fetch's verified coverage that Canvas no longer returns (deleted assignments or events, cleared due dates, dropped or inactive courses) are flagged withdrawn in `canvas_record_status`. Rows are never deleted. Withdrawn records leave the Timeline, assignments and scheduling; local progress and audit entries remain, and a record that returns is reinstated. Coverage excludes courses or events that returned 403/404, and any other failure aborts the sync before it touches the database. Tests use fixture responses only. `AssignmentAnalysisProvider` currently has a fixture-only provider and deterministic output validation, not an inference backend. The scheduler consumes local availability, protected rest windows, and imported fixed events and returns local proposals. The separate CalendarAwarePlanning entry point adds user-requested Apple Calendar busy intervals; AppleCalendarService publishes only an explicitly approved preview through EventKit. Canvas and Microsoft tokens use macOS login Keychain ACLs. Local packaging uses the unchanged bundle identifier and a stable Apple Development signature; it does not add entitlements or change credential records. Microsoft Graph multi-account authentication, read-only Inbox sync, and local analysis are implemented with mocks; real authentication awaits user registration/consent and interactive testing. The implemented EventKit adapter requires user-initiated full access and separate calendar/setup/publication approval; development uses only mocks. See `tasks/STATUS.md` for remaining acceptance work.

## Outlook implementation decision (2026-10-19)

- Native AuthenticationServices + explicit authorization-code/PKCE protocol keeps the existing dependency footprint small. A public Entra app ID and registered callback are required; no client secret is embedded. OAuth state and challenge are generated with system cryptographic randomness. Account identity is established by Graph `/me`, not by decoding an unverified ID token. Login, test, refresh, and sync use injected transports for tests.
- `OutlookState` lives under a namespaced `app_settings` SQLite row. It holds account metadata, cursors, revision hashes, rules, and review proposals; credentials are exclusively in `MicrosoftCredentialStore`/Keychain. Import and review commit atomically with canonical source/event/audit records. Existing schema and Canvas progress tables are preserved. This compact store suits the current single-user application; large histories should move to indexed tables before scaling.
- The shared app-level `OutlookViewModel` prevents overlapping UI/polling operations across windows. Each request creates a per-account session that refreshes credentials through a coalesced task. Polling uses persisted settings and backs off after failed attempts. The same sync function can later be triggered by authenticated change notifications; no listener or subscription exists yet.
- Message/attachment text is untrusted data. `EmailAnalysisProvider` output is validated for source/account identity, evidence, confidence, pending decision, and limits. The implemented provider runs locally and handles explicit dates conservatively. Cloud providers are disallowed until a separate disclosure/consent configuration is implemented.
- Pending email proposals do not enter planning. Explicit local approval creates protected canonical events or deadlines; reviewed cancellation/reschedule advisories preserve existing events. Demo sources remain excluded from real planning and conflict checks. Exact title/kind/start/duration duplicates merge provenance; conflicting proposals remain visible for human review.

## Apple Calendar boundary

The native adapter, approval service, busy-time planning wrapper and SwiftUI controls live in separate Calendar files. An atomic ownership journal stores app-owned mappings, write intents, audit and undo without adding a SQLite migration. Personal event snapshots remain in memory. Every update/cancellation checks the dedicated calendar ID, per-event UUID marker and last-confirmed snapshot; ambiguous outcomes disable further publication pending read-only reconciliation. See [APPLE_CALENDAR.md](APPLE_CALENDAR.md) for contracts, safety limits and merge guidance.

## Combined main integration (2026-10-19)

- Connections hosts the existing Canvas controls, multi-account Outlook controls, and Apple Calendar controls together. The shared app-level planner owns the Calendar service/UI state; Outlook remains shared across windows. Creating the UI does not construct an EventKit store or request access.
- Both Canvas sync and Outlook import/review invalidate the local study proposal and any Calendar approval preview. Outlook reload invalidates before reading SQLite so a failed reload cannot leave an approval based on superseded commitments. Completion, estimates, availability, and mode changes also invalidate previews.
- The Calendar planning wrapper consumes the same live/demo dataset and local completion table as the original planner. Approved Outlook events and Canvas commitments remain hard constraints alongside transient Calendar busy intervals. Pending mail and demo records cannot enter live planning; completed/overdue work stays excluded. Calendar publication never changes mailbox contents, Canvas records, or assignment completion status.
- No schema migration or credential-store change is introduced by this merge. SQLite retains imported data, Outlook state and completion choices; the independent ownership journal retains only managed-event state. The bundle contains both the Microsoft OAuth callback scheme and Calendar full-access usage description. Development packaging preserves the same bundle identifier under the certificate-backed signing workflow documented in [DEVELOPMENT_SIGNING.md](DEVELOPMENT_SIGNING.md).
- Automated combined coverage uses temporary SQLite, mock Calendar events and synthetic Outlook review records, including repeated Canvas import and database reopen. Live permissions, OAuth, actual accounts and UI interaction remain user-led acceptance checks.

## Unified Apple Calendar Timeline (2026-10-19)

- AppleCalendarService projects busy EventKit occurrences into an in-memory AppleCalendarTimelineEvent; it does not create source records or SQLite rows. At launch, the Timeline checks EventKit's persisted authorization state without requesting access. When full access already exists, it initializes the connection and reads the active Day, Week, or Month range. EventKit change notifications then refresh that range while the app runs.
- The projection treats external busy events as protected commitments and retains each title only in the in-memory Timeline value used for local rendering. It retains no notes, locations, attendees, URLs, calendar account names, or other personal metadata. A process-local normalized title hash exists only long enough to collapse an exact Canvas/Outlook mirror; neither the hash nor the title is serialized. App-owned sessions are recognized only by the existing journal marker and last-confirmed record, and remain the only sessions eligible for change.
- EventKit returns recurring occurrences expanded within the queried range. Occurrence IDs include the start/end instant so separate recurrences display separately. All-day state is carried through the projection and old ownership journals decode with `isAllDay` defaulting to false. Timeline filtering uses date-interval overlap, so multi-day/all-day commitments appear in every applicable Day, Week, and Month view.

## Calendar redesign — Stage 1 (2026-10-19)

- `CalendarPresentation` in AcademicCore is a pure display layer over `UnifiedTimelineEvent`. It computes locale-first weekdays, complete month rows, exclusive visible intervals, source filtering, and clipped per-day event placements. The UI and the existing authorized Calendar loader use the same visible interval, including adjacent-month cells. All-day occurrences use a separate scrollable band; timed occurrences spanning midnight are clipped independently on each day.
- Overlap placement uses deterministic interval partitioning: connected groups share the maximum required lane count, touching intervals reuse lanes, and later independent groups regain full width. Coordinates are elapsed minutes from local midnight, preserving actual durations through DST. Days with transitions label their own local hours and time-zone abbreviations, including the repeated hour; their elapsed grid can be 23/25 hours (or a fractional-hour transition). Zero-duration deadline instants receive a clipped 15-minute display marker; the original source times are never changed.
- `CalendarPresentationState` belongs to each ContentView/window and survives navigation between app pages and calendar dates/views. It holds selected date/view, source visibility, task-panel visibility and an event ID, with no event titles or persisted personal data. Selection resolves against the current data-mode projection; the inspector dismisses on mode change. This is session UI state, not a new database preference or schema.
- Modular SwiftUI files own the mini-calendar/source sidebar, workspace navigation, time grid, month grid, event blocks/details, and academic task panel. The NavigationSplitView sidebar and HSplitView task pane resize natively. Narrow calendars scroll horizontally to preserve usable day columns; time headers stay above the vertical timeline, and large all-day lists scroll separately. The toolbar toggles tasks; Command-Left/Right navigates, Command-T selects today, and Command-Option-Backslash toggles tasks. Native buttons, checkboxes, segmented controls and status menus support focus/keyboard use; labels, icons, source text and distinct deadline borders supplement color.
- Filters affect display only. All protected commitments remain in the unfiltered dataset used by scheduling and approval. Canvas is blue, approved Outlook purple, Apple Calendar orange, and journal-owned sessions green. Demonstration/unknown records remain explicitly labelled. Apple Calendar titles remain verbatim, transient and local, as before. Inspector source links allow only HTTP(S).
- Academic tasks read the same scoped assignments, SQLite progress status, and window-local effort/priority dictionaries as Plan preview. Changing status calls the existing save/invalidation function; no parallel progress store is introduced. Effort and priority appear when the user has set them in Plan preview; no AI estimate is invented. Overdue, undated and completed groups remain visible with their existing scheduling eligibility.
- Stage 1 adds no Calendar mutations, drag-and-drop, resizing, creation, migration, OAuth, cloud transmission, or changes to connector/approval code. All new layout/filter tests use synthetic values. Live acceptance and VoiceOver/keyboard interaction remain user-led. Stage 2 needs separate approval.

## Apple Reminders — Stage 1, read-only (2026-10-20)

`RemindersClient` (read-only protocol) → `EventKitRemindersClient` adapter → `RemindersSyncService` (permission-gated sync, dedup, deletion/missing-list handling, coalesced change observation, 5-minute refresh) → in-memory `RemindersSnapshot` → `RemindersPresentation` (pure upcoming/tree/marker helpers) → SwiftUI (`RemindersUI.swift`). Reminders are due-date markers, not events: they bypass `UnifiedTimeline`, the scheduler and busy-time queries. Content is memory-only; no schema migration. Write capabilities must arrive as a separate protocol in a later, separately approved stage. See [APPLE_REMINDERS.md](APPLE_REMINDERS.md).

## Interactive calendar — Stage 2 (2026-10-20)

- `CalendarSessionDraft` and `CalendarInteraction` are pure, transient proposal state and 15-minute grid transformations. Moving preserves duration; resizing preserves start. Coordinates use elapsed minutes from local midnight, including distinct repeated DST hours. Creation uses a stable UUID key, retained through edit/preview retries. Scheduled sessions retain their original task/session key; interactive movement never recalculates an ordinal or silently modifies another session.
- `CalendarStudyInteraction` adds pointer move/resize and an accessible edit action only for journal-owned, unchanged timed sessions. `CalendarTimeGrid` adds empty-slot selection and a dashed proposal overlay. `CalendarSessionEditor` shares the same proposal path for pointer, keyboard and VoiceOver users. The exact review state is separate from editing; only the explicit approval button calls the mutation service. Month retains inspection/day navigation; date fields allow edits beyond the visible range. Gesture edge auto-scroll is not implemented.
- `AppleCalendarService.previewSession` checks the draft's original snapshot against current ownership, validates dates, and prepares one exact change. It reuses `approve`, durable write intents, marker checks, cancellation, recovery and undo. Retrying the same creation ID is a no-op if its exact values already exist; a changed retry is rejected. Dismissing invalidates approval. Each service has a single active preview, so a newer preview in another window invalidates the older one.
- A throwing `liveItems` provider re-reads SQLite and applies `AcademicDataset` live provenance before conflict checking at preview, approval and immediately before each mutation, including undo. UI filters cannot remove commitments; storage read failure blocks writes. Canvas and approved Outlook fixed intervals and local study sessions join freshly queried EventKit busy intervals. Authoritative deadline instants are unchanged and are not treated as artificial busy durations. Manual sessions are user-defined blocks, not new assignment records or automatic workload/deadline changes.
- The Timeline exposes an optional journal key only when the observed event matches the last-confirmed snapshot, calendar and marker and is safe to modify. Personal, externally edited, recurring and all-day events receive no editing capability. Authorization is checked again in the service; the presentation key is not sufficient authority to write.
- Production no longer references `SampleData`, which moved into the test target. `PlannerViewModel` always scopes live data and reports storage failure without fixture fallback. Existing database rows and completion choices remain intact; no migration, dependency, signing, icon, bundle identifier, credential or OAuth configuration changes are needed.
